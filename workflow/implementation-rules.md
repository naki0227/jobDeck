# JobDeck Workflow Rules

この文書は、JobDeck を実装する際に毎回参照する作業ルールです。
以後の実装では、このファイルの内容を優先して判断します。

## 1. 前提

- このプロジェクトでは、まずフロントエンドを実装する
- バックエンドは後続フェーズで、ユーザー本人が主体となって実装する
- AI 機能を使う前提でも、フロントエンドは API 未実装状態で進められるように設計する
- 個人情報を扱うため、利便性より先に安全性を確認する

## 2. 役割分担

### この段階で私が担当すること

- iOS フロントエンドの設計と実装
- SwiftUI 画面
- SwiftData モデル
- ローカル状態管理
- フロントエンド向けの API 契約定義
- テスト可能な範囲のテスト実装
- 実装内容の丁寧な説明

### この段階で私が担当しないこと

- 本番バックエンド実装
- サーバー側の本番課金処理
- 本番認証基盤の構築
- API キー運用の本番設定作業

## 3. コミット方針

コミットは細かく分けます。

原則:

- 1 コミット 1 関心ごと
- 機能単位で区切る
- コンポーネント追加はできるだけ独立させる
- 状態管理追加も独立させる
- テストを追加できる変更は同じコミット、または直後の対応コミットに含める

コミット粒度の例:

- `add company model and sample data`
- `build company list screen`
- `add company detail form`
- `implement episode creation flow`
- `add interview deck tests`

避けること:

- 無関係な変更を 1 コミットに混ぜる
- UI と大規模リファクタをまとめる
- テスト可能な変更なのにテストを後回しにする

## 4. 実装順ルール

実装は次の順で進めます。

1. Workflow を確認する
2. 仕様の対象範囲を固定する
3. 影響ファイルを調べる
4. 小さく実装する
5. テストできるものはテストする
6. 何を実装したか、どう確認したかを共有する

今後こちらが実装を進めるたびに、この Workflow を参照して進めます。

## 5. バックエンド連携の進め方

バックエンドは、フロントエンド完成後に進めます。

その際のルール:

- 初学者向けに説明する
- 用語はできるだけ噛み砕く
- なぜその設計にするのかを先に説明する
- すぐ完成コードを丸ごと渡すのではなく、理解しながら組み立てられるように案内する
- コピペ前提ではなく、段階的に書けるように教える
- 実装後はリクエスト、レスポンス、エラーハンドリングの意味も説明する

推奨バックエンド候補:

- 第一候補: Rust
- 第二候補: Go
- TypeScript は Workers を最短で組みたい場合の選択肢として残す

補足:

- すでに Rust の API 実装経験がある前提で進める
- 将来バックエンドに入るときは `axum` ベースを第一候補として案内する

## 6. セキュリティルール

このアプリは個人情報を扱うため、次を必須ルールにします。

- API キーをアプリに埋め込まない
- 機微情報をログ出力しすぎない
- AI に送る内容はユーザー確認を挟む
- ローカル保存データの責務を明確にする
- 通信層は将来の認証追加を想定して抽象化する
- ダミーデータと実データの混線を防ぐ
- テストデータに個人情報を使わない
- 失敗時に過剰な内部情報を画面に露出しない

## 7. テストルール

テストできる変更には、できるだけテストを含めます。

対象例:

- モデル変換
- ViewModel の状態遷移
- バリデーション
- ユーティリティ
- 依存注入されたサービス

補足:

- UI 全体の見た目だけでなく、ロジックの確認を優先する
- テストが難しい場合は、なぜ難しいかを明示する
- 未実施のテストは必ず共有する

## 8. 説明ルール

各実装のあとには、少なくとも次を共有します。

- 何を実装したか
- なぜその分け方にしたか
- どこに責務を置いたか
- どう確認したか
- 残っている課題は何か

必要に応じて、ファイル単位でも説明します。

## 9. 将来の実装で追加していくルール

現時点で追加しておく運用ルール:

- 新しい仕様は、まず `docs` に反映してから実装する
- 実装開始前に、影響範囲とコミット単位を意識する
- AI 依存の仕様は、フロント側ではモックで代替できるようにする
- 画面が完成しても、保存導線とエラーハンドリングが弱ければ未完成とみなす
- 設定値、環境差分、課金状態はハードコードしない

## 10. 初回の開発優先順

まずは次を優先します。

1. SwiftData モデル
2. 企業一覧
3. 企業詳細
4. エピソードカード
5. 企業とエピソードの紐付け
6. 逆質問カード
7. 面接ログ
8. 面接前 10 分デッキ
9. AI なし自己分析導線
10. AI 連携用の土台

以後、実装時はこの順序をベースに調整します。
